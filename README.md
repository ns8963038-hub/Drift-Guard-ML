# DriftGuard

A multi-user platform for monitoring machine learning models in production, and
detecting when the data they see stops resembling the data they were trained on.

For every batch of incoming production data it answers four questions:

| Question | Module |
|---|---|
| Is the incoming data clean? | Data quality — missing values, duplicates, outliers, unseen categories, type mismatches |
| Does it still look like the training data? | **Drift detection** — K-S, Chi-Square, PSI and Jensen-Shannon, per feature |
| Is the model still accurate? | Performance — accuracy, precision, recall, F1, error rate |
| Overall, how healthy is this model? | A single 0–100 health score |

…then raises alerts when thresholds break, explains *why* in plain English, and
recommends retraining. **It never trains or retrains anything** — the
recommendation is advisory.

---

## Requirements

**Python 3.11 specifically.** Not 3.12, not 3.13, not 3.14 — Django 5.0 does not
support them, and the system Python on a recent macOS install is 3.14.

```bash
# macOS
brew install python@3.11

# Ubuntu / Debian
sudo apt install python3.11 python3.11-venv
```

No other services are required. No Redis, no Celery, no database server — SQLite
in development, and the scheduler runs inside the web process.

## Setup

From a clean clone:

```bash
# 1. Environment
python3.11 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 2. Demo data — downloads Telco Churn and Adult Income, cleans and splits them
python scripts/prepare_datasets.py

# 3. Demo models — trains 4 scikit-learn Pipelines and validates each one
python scripts/train_demo_models.py

# 4. Verify
pytest
```

Expected: **216 tests passing**.

Step 2 needs an internet connection **once**; raw files are cached under
`data/raw/` and every later run reuses them.

Neither `data/` nor `artifacts/` is committed — both are regenerated by those two
scripts, so the repo stays free of large binaries and everyone gets byte-identical
inputs from the same fixed seeds.

## Architecture

```
views/     HTTP. Parse, authorise, delegate, render. No business logic.
   │
services/  ORM-aware orchestration. Owns transactions. The only layer that writes.
   │
engine/    Pure Python. DataFrames in, dicts out. NO Django import, ever.
   │
models/    Django ORM. Persistence only.
```

### The rule that shapes everything

**`monitoring/engine/` may not import Django.** It takes DataFrames and dicts and
returns dicts. Three consequences, all intended:

1. The statistical core is unit-testable with no database and no HTTP request —
   which is why it has 216 tests and 95% coverage while the web layer is still
   being built.
2. Every way data can arrive (CSV upload, the scheduled simulator, the REST
   endpoint) converges on one `run_monitoring()` call. Adding a fourth means
   adding a caller, never a second pipeline.
3. The maths can be demonstrated standalone, in a notebook, with no server
   running.

### The five stages of a monitoring run

```
quality  →  drift  →  performance  →  health  →  explain
```

Quality runs first because its findings — unseen categories, missing-value spikes
— are context for reading the drift results that follow.

Two developers, split by directory ownership. **Read
[WORK_SPLIT.md](docs/WORK_SPLIT.md) before writing anything.**

> ⛔ **`monitoring/` and `simulator/` already exist.** `django-admin startapp`
> fails on a non-empty directory, and deleting either would destroy the engine.
> The correct commands are in WORK_SPLIT §6, Phase 0, task 1.

House rules:

- Merge to `main` at least daily. Long-lived branches are how this fails.
- `pytest` green before every push.
- `ruff check` and `black` clean.
- Engine coverage stays ≥ 90%.
- Never commit `db.sqlite3`, `.env`, `media/`, `data/` or `*.joblib`.

## Known limitations

Stated openly rather than discovered later.

**Uploaded model files execute code on load.** `joblib.load` deserialises
arbitrary Python. This is inherent to the format and is *not* solved here.
Mitigations: no public registration, upload restricted to Admin and Data
Scientist roles, extension/size/MIME validation, SHA-256 recorded per artifact,
and artifacts are never served back to browsers. Accepted risk, documented as R1
in the PRD.

**Single worker only.** The scheduler runs inside the web process, so
`runserver --noreload` or `gunicorn --workers 1`. Two workers means two
schedulers and duplicate batches. Moving the scheduler to its own process is
about half a day's work and is deliberately out of scope.

**Performance metrics need labels.** Real production data usually arrives without
ground truth. Batches without a target column still get full drift, quality and
prediction-distribution analysis; the accuracy metrics are recorded as
unavailable — never as zero — and the health score redistributes its weights
accordingly.

**Tabular scikit-learn classification only.** Artifacts must be `Pipeline`
objects accepting raw feature columns. No TensorFlow, PyTorch, regression, or
non-tabular data.
